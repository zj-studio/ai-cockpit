# 需求确认 · 协同面"两套独立后台 + 驾驶舱统一只读视图"

**定调人**：老板（宥初）
**记录**：初墨　**日期**：2026-09-12 18:49
**效力**：老板原话定调，作为 v0.3.1 → v0.4 修订的最高界面/范围约束；与既往"统一控制面统管 Dify"理解冲突的，以本记录为准。

## 一、核心区分：分管 ≠ 分看
- **管理层（怎么管/派单/凭据）＝两套独立后台，物理隔离，永不合并。**
- **视图层（老板怎么看）＝驾驶舱内一个统一页面，只读看到两边所有 agent 的工作情况。**

## 二、两套后台（管理边界）
1. **Dify 内（第一套）**：小墨 + 9 名员工 = 10 个 app，沿用现有驾驶舱 / Dify 管理（总览、在岗大厅、研讨室、知识图谱等不动）。
2. **Dify 外（第二套）**：Codex(砚舟)、WorkBuddy(旺财)、Coze(初墨)，TraeWork(9527) 仅预留——共 4 个，走新建的协同控制面。
3. 两套之间：**不合管、不跨域派单、不共享凭据、不汇控制数据**。小墨不进外部协同派单体系。
4. 因此 v0.3.1 中"Dify Adapter 后续接入 / MVP-2 Dify 只读 / MVP-3 Dify 受控写 / 跨域派单 / 统一控制面统管 Dify"等**管理合并内容删除**。

## 三、统一视图（老板的硬性诉求）
- 在**现有驾驶舱内**提供一个统一查看页面，老板一处看到 **10（Dify 内）+ 4（Dify 外）= 14 个 agent** 的工作情况。
- 性质＝**只读聚合展示**：
  - 外部 4 个的任务/进度/阻塞/风险/费用/产物/待审批/审计，由协同面以**只读接口**供驾驶舱展示层读取；
  - Dify 内 10 个状态沿用驾驶舱现有数据源；
  - **只合显示，不合控制**：该页面不得形成任何跨系统写操作、跨系统派单或凭据互通；审批与处置仍回各自原系统完成。
- 现有驾驶舱任何现有页面不改动、不重做。

## 四、入口形态（团队设计，报老板审批，勿自行定死）
- 候选 A（初墨倾向）：驾驶舱新开一级"工作总览/协同看板"，内部分"Dify 员工组 / 外部协同组"两个清晰分区。
- 候选 B：在现有员工在线管理（在岗大厅）页内增加"外部协同"模块。
- 理由：外部 4 个为协调/技术 agent，语义不同于 Dify 内容员工，初墨判断硬并入在岗大厅易混淆；最终以砚舟专业设计 + 老板拍板为准。

## 五、给砚舟的修订要求（v0.4）
1. 范围收敛为 Dify 外 4 agent 协同，删除全部 Dify 管理合并内容，文档建议更名《Dify 外 Agent 协同控制面方案》。
2. 新增"驾驶舱统一只读视图"章节，明确只读聚合、无跨写/跨派/凭据互通，并给出 A/B 入口候选与推荐。
3. MVP 重排：控制面核心 → Codex+WorkBuddy → Coze →（后续）TraeWork；统一只读视图的接入时点在方案中写明。
4. 初墨、旺财在 v0.3.1 的"通过"基于旧范围；范围变更后仅做一次快速范围确认，不重新铺开审查。
