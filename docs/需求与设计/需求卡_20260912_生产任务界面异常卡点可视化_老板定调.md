# 需求卡 · 驾驶舱"生产任务"界面必须显式呈现任务异常与卡点

**定调人**：老板（宥初）原话："像小墨派单出现问题，就该体现到我驾驶舱下的生产任务界面上，我可以看到任务问题情况，卡在什么地方。"
**记录**：初墨　**日期**：2026-09-12 19:03
**承接**：是 18:49《驾驶舱统一视图与两套独立后台》需求在"生产任务/异常态"上的具体化；并将压测台账 003（六站看板为静态演示数据）从"接真实数据"升级为"真实数据 + 显式异常"。
**合规**：只读呈现，跨系统不写、不派单、不通凭据（沿用 18:49 定调）。

## 一、老板要的效果
在驾驶舱"生产任务"界面，看到每一个真实任务的状态；**任务一旦异常，不用问人，界面直接标出：卡在哪个环节、什么原因、什么时间发生、归谁处理、处理到哪一步**。正常任务看进度，异常任务看卡点。

## 二、现状（做不到的原因）
1. 现有"六站流程追踪"是预置演示样例（公众号短文/PPT美化/电商主图/探店图文四张假单），真实任务不进轨道——台账 003。
2. 小墨自动派单链路当前不通（台账 002/005/006），没有真实任务号与状态数据可供呈现。
→ 所以本需求依赖链路修复产出真实状态，但**界面与字段定义先行设计**。

## 三、界面要呈现的内容（供砚舟设计，最终老板审批）

**A. 每个任务的正常状态链**
待派单 → 已派单（必须带真实任务号）→ 员工执行中 → 已交稿 → 验收中 →（打回，记次数）→ 完成。

**B. 异常态必须单独可见、红字/置顶或筛选（本次需求重点）**，至少覆盖：
- 派单失败·模型自产无任务号（对应本次小墨 002/H1）
- 通道不通（relay / dispatch / executor 异常，对应 H2/006）
- 路由不命中（岗位名找不到目标员工，如缺"华安"，对应 H3/005）
- 员工超时未接单 / 执行中超时
- 执行报错（沙箱、出网、工具失败等）
- 验收打回（记打回次数，超限升级）
- 会话/上下文异常（多轮丢上下文，对应 004）

**C. 每条异常至少带字段**：任务号、客户/需求来源、目标岗位、当前卡住环节、原因分类、发生时间、责任处理人、处置状态（待处理/处理中/已修复待复测/已关闭）、关联证据或回执。

**D. 提醒**：阻塞、失败、红线类异常要强提醒（对接 v0.3.1 通知策略：审批/红线/阻塞/失败/完成强提醒），不能只埋在列表里。

## 四、数据来源与边界
- Dify 内小墨派单/员工执行/验收状态 → 由第一套（现有驾驶舱/Dify）数据源供数；
- Dify 外 4 个 agent 的协同任务卡点 → 由外部协同面只读接口供数；
- 在驾驶舱统一只读视图同屏可见，但**只合显示、不合控制**，处置仍回各自原系统。

## 五、落地顺序（建议，报砚舟排期、老板拍板）
1. 先修小墨派单链路（见《请求卡_20260912_小墨派单链路诊断整改》），让系统产生真实任务号与环节状态；
2. 砚舟同步设计"生产任务 + 异常卡点"界面（可用现有假数据先出原型给老板看样式）；
3. 链路通后接真实数据流，替换六站演示数据，异常态按本卡 B/C 落地；
4. 与 003 看板真实数据改造合并为一项，不重复建设。

## 六、系统上线前的人工兜底（初墨现在就能做）
在界面接通真实数据前，初墨按本卡字段，用任务台账/在办台账人工维护"任务卡点视图"，每次有任务异常主动按"任务→卡住环节→原因→责任人→状态"汇总报老板，先保证老板"看得到卡点"，不依赖系统。
